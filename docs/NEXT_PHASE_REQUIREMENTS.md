# AAISE Architectural Enhancements & Requirements Backlog

## Overview
This document records the 7 core platform modifications requested by the user to enhance database auditability, agent topology flexibility, human governance, iteration control, QA reporting accuracy, LLM telemetry, and interactive chat responsiveness.

---

## 1. Database Audit Restructure (Audit Trails Across All Tables)
### Requirements
- Every database entity in `src/infrastructure/db/models.py` must include consistent audit tracking columns:
  - `created_date` (`created_at`): Timestamp with timezone, defaulting to UTC when the record is created.
  - `created_by`: User or Agent identifier (defaulting to `"system"` or `"human_operator"`).
  - `updated_date` (`updated_at`): Timestamp with timezone, automatically refreshed on record update.
  - `updated_by`: User or Agent identifier indicating who last modified the record.
- **Affected Tables**:
  - `projects`, `project_agent_configs`, `project_files`
  - `git_repositories`, `git_release_manifests`
  - `workflow_runs`, `workflow_checkpoints`, `workflow_events`
  - `conversations`, `messages`, `human_approvals`, `token_usages`
  - `requirements_specs`, `technical_design_docs`, `test_specifications`
  - `defect_logs`, `security_scans`, `qa_test_runs`, `execution_processes`
- **Migration Strategy**:
  - Implement an abstract/base model mixin (`AuditModelMixin`) in SQLAlchemy 2.x.
  - Generate an Alembic migration script to evolve the SQLite schema cleanly while preserving existing data.

## 2. Independent Toggleability for All 5 Agents (Full Topology Freedom)
### Requirements
- Previously:
  - **Agent 1** (Doc Reviewer) and **Agent 3** (Main Coding Agent) were marked as mandatory invariants (`is_mandatory = True`).
- New Specification:
  - **All 5 agents must be 100% independently toggleable ON/OFF**:
    - Agent 1: Documentation Reviewer & Spec Creator (Can be toggled OFF)
    - Agent 2: Mock Vendor API Developer (Can be toggled OFF)
    - Agent 3: Main Coding Agent (Can be toggled OFF)
    - Agent 4: Independent Black-Box QA Engineer (Can be toggled OFF)
    - Agent 5: Static Security Reviewer (Can be toggled OFF)
- **Backend & LangGraph Changes**:
  - Update `get_default_agent_specs()` and `ensure_project_agent_configs` in `src/api/routes/projects.py`.
  - Update `src/infrastructure/orchestration/graph_builder.py` so the state graph dynamically routes around any disabled agent (including starting directly at Agent 3 if Agent 1 is disabled, or stopping after Agent 1 if Agent 3 is disabled).
- **Frontend Changes**:
  - Update `frontend/components/AgentConfigModal.tsx` and sidebar status pills to allow toggling Agent 1 and Agent 3 without disabled/locked switches.

## 3. Human Approval Gate After Every Agent Execution
### Requirements
- Previously:
  - Human approval occurred after Agent 1 TDD generation and before final release promotion.
- New Specification:
  - **Every single active agent execution must trigger a Human Approval Checkpoint**:
    1. Agent 1 finishes Specs $\rightarrow$ **Human Approval Required** $\rightarrow$ (Approve / Request Revision).
    2. Agent 2 finishes Mock APIs $\rightarrow$ **Human Approval Required** $\rightarrow$ (Approve / Request Revision).
    3. Agent 3 finishes Code $\rightarrow$ **Human Approval Required** $\rightarrow$ (Approve / Request Revision).
    4. Agent 4 finishes QA Test Run $\rightarrow$ **Human Approval Required** $\rightarrow$ (Approve / Request Revision).
    5. Agent 5 finishes Security Scan $\rightarrow$ **Human Approval Required** $\rightarrow$ (Approve / Request Revision).
- **Workflow State & Engine**:
  - LangGraph graph nodes will pause execution using durable checkpoints (`interrupt_before` or conditional human approval evaluation nodes).
  - Web UI displays the agent's work/diff/results and waits for the user to approve or reject with feedback before proceeding to the subsequent agent.

## 4. Strict Iteration Cap at 2 & Bug Resolution
### Requirements
- Previously:
  - Default iteration count was 3, and a bug allowed remediation loops between QA/Security and Agent 3 to continue past the threshold.
- New Specification:
  - The iteration count must strictly cap at **maximum 2 iterations**.
  - If defects or security findings remain after 2 cycles, the orchestrator must halt immediately, mark the workflow state as `ESCALATED_TO_HUMAN`, and present full defect findings to the operator without looping again.

## 5. QA Report Clarity & Authenticity Overhaul
### Requirements
- **Problem**: Current QA test reporting is unclear, lacks granular execution details, and at times produces inaccurate or ambiguous status representations.
- **New Specification**:
  - QA reports generated by Agent 4 must provide verifiable, clear, contract-level HTTP evidence:
    - Target endpoint URL and HTTP Method
    - Request payload and query parameters sent
    - Response status code, latency (ms), and exact response body received
    - Expected vs. Actual contract comparison
    - Clear categorization: `PASSED`, `FAILED`, or `SKIPPED (MANUAL_QA_ELECTED)`
    - Actionable defect logs with reproducible cURL commands for any failure
  - UI Test Results tab must render this in a clear, filterable table/accordion view instead of raw unformatted markdown.

## 6. Fine-Grained Token Consumption, Cost & Latency Tracing per Request
### Requirements
- **Problem**: There is no live trace showing how many tokens were consumed, how long the LLM took, or the exact cost per agent request.
- **New Specification**:
  - Every LLM interaction through `LiteLLMAdapter` / `OllamaAdapter` must measure and record:
    - `prompt_tokens` (input tokens)
    - `completion_tokens` (output tokens)
    - `total_tokens`
    - `latency_ms` or `duration_seconds` (time taken by LLM to return response)
    - `estimated_cost_usd` (computed via model pricing config)
    - `model_name` and `provider`
  - Persist this telemetry in the `token_usages` database table linked to `workflow_run_id`, `project_id`, and `agent_type`.
  - Expose telemetry in the chat UI: each agent message and workflow step will display a pill/badge showing `Tokens: X in / Y out | Latency: Z.Zs | Cost: $0.00XX`.

## 7. Chat Query Contextual Responsiveness & Execution Stop/Abort Control
### Requirements
- **Problem 1 (User Queries Ignored)**:
  - If a user sends a specific message or query in the chat box (e.g., providing an SRS and typing *"Explain point 9"* or asking a specific question to Agent 1), the system ignores the text and triggers default batch orchestrator flows instead of answering the user's specific query.
- **Solution 1**:
  - Implement intent classification in `src/application/chat/chat_service.py`:
    - Distinguish between **Workflow Directives** (*"Build project"*, *"Run workflow"*) and **Ad-hoc Conversational Inquiries** (*"Explain point 9 in the SRS"*, *"What does this error mean?"*).
    - When a conversational query is detected, route it directly to the designated agent (e.g. Agent 1) in Q&A mode, streaming the direct explanation back into the chat without triggering the full multi-agent state graph.
- **Problem 2 (No Stop / Cancel Button)**:
  - When an agent or workflow is executing, the user has no way to halt or abort the operation mid-flight.
- **Solution 2**:
  - Add a **Stop / Cancel** button in the chat interface toolbar (red stop icon next to the send button while running).
  - Backend API endpoint `POST /api/v1/workflow/{run_id}/cancel` to set an abort flag on the execution thread and terminate any running Docker container or LLM streaming task immediately.
